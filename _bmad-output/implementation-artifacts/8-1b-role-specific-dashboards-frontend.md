## Story

As a Teacher, an Admin/Owner, or a Student,
I want a role-specific dashboard at `/dashboard` that shows the information and actions most relevant to my role immediately after login,
so that I see my next sessions, what needs my attention, and my one-click paths into the work — over the role-scoped read shipped in 8-1a.

Frontend slice only. The role resolution, the per-role aggregation, and the R31/PERF-2 query-count + no-Seq-Scan harness were built + tested in **8-1a** and are already generated into `src/lib/api/client.ts` (marked **PROVISIONAL — 8-1b co-finalizes**, D13). This story is the **sole consumer**: one fetch, three distinct role dashboards (UX-3), plus the split of the existing Epic-2 onboarding shell from the real teaching dashboard.

## Decisions (D1–D16 — all SPEC; D12 & D14 carry Ducdo product rulings 2026-09-15)

- **D1 — One role-branched `/dashboard`; retire the `/student` stub.** `/dashboard` (`routes.tsx:204-214`) stays the single **ungated** landing for every authenticated role (all sidebars + post-login redirect already point here — `sidebarNavConfig.tsx:102`, `sanitizeNextParam.ts` default, `acceptInvite.ts:95`). Introduce a `DashboardRoute` dispatcher that reads `useRole()` + `useRoleLoading()` and renders **three separate components** (UX-3): `<OwnerDashboard>` (role `owner` **or** `admin`, D9), `<TeacherDashboard>`, `<StudentDashboard>`. While `useRoleLoading()` is true → render `RouteAccessCheckingCard`/skeleton (**never flash the wrong dashboard mid-hydration** — mirror `RouteRoleGate`'s precedence). **Retire** the `/student` route (`routes.tsx:193-203`, a dead stub with no gate and nothing navigating to it) and drop its standalone mount. Keep `/dashboard` free of `RouteRoleGate` (all roles legitimately land — the branch is content, not access).
- **D2 — Split the Epic-2 onboarding shell from the real teacher dashboard; PRESERVE the onboarding branch.** `TeacherDashboard.tsx` (`307` lines) today is an **onboarding** surface driven by `useOnboardingProgress()` (persona dispatch → `WelcomeBackBanner` + `FinishSetupCard` checklist + placeholder persona bodies). Keep the **onboarding-incomplete** branch UNCHANGED — when onboarding is incomplete it still renders the banner + finish-setup checklist (Story 2-4/2-5a owns that machinery: `WelcomeBackBanner`, `FinishSetupCard`, `useChecklistState`, `checklistDefinition`). When onboarding is **complete**, render the real 8.1 teacher dashboard (week-strip + 3 rails) in place of the persona placeholder bodies (`SampleDashboardPreview`/`FirstAIGradeCard`). Reuse the `DashboardSkeleton` loading pattern (`:111-124`) and the `stableProps` refetch-race latch approach (`:168-201`, W-BLOCKER-2). Do NOT delete onboarding code. **Flag to Sally/Ducdo:** exact composition when a teacher is onboarding-complete but has zero real data (empty rails) — default is the real dashboard with UX-1 empty states, not the ghost preview.
- **D3 — Fetch = ONE page-level `useDashboard` via `apiFetchWithMeta` (`meta.serverTime` is load-bearing).** New `src/features/dashboard/api/dashboardKeys.ts` (`{ all: ['dashboard'] as const, data: () => [...all,'data'] as const }`) + `useDashboard.ts`: `useQuery({ queryKey: dashboardKeys.data(), queryFn: () => apiFetchWithMeta<DashboardData, EnvelopeMeta>('/api/dashboard') })`. **Use `apiFetchWithMeta`, NOT `apiFetch`** — the plain unwrap DROPS `meta`, and every countdown / "N ago" / "live now" computation needs `meta.serverTime` (D16). Component owns the query (FW-1 pragmatic, per [[feedback_pragmatic_interpretation_of_spec_absolutes]] + the 7-2b/7-1b D2 shipped norm — no loader-prefetch exists app-wide). One fetch feeds all three blocks; `staleTime` per FW-3 (30s default acceptable; document any override). Model on `features/schedule/api/useSessions.ts` + `sessionsKeys.ts`.
- **D4 — Consume the generated types verbatim; no Zod for the read.** `import type { components } from '@/lib/api/client'`; reference `components['schemas'][…]` for every `Dashboard*` shape + `EnvelopeDashboard`/`EnvelopeMeta` (full list in Dev Notes). Never hand-write these (TS-2/XL-1). The project generates **only** openapi-typescript for wire reads — **no Zod schema exists or should be created** for `/api/dashboard` (Zod is form-validation only here; this is a read).
- **D5 — Lean `DashboardWeekStrip` + session-row renderer; do NOT reuse `SessionBlock`.** `SessionBlock` (`features/schedule/components/SessionBlock.tsx:25`) is typed to `SessionWire` (`classColor`/`id`); dashboard sessions are the **leaner `DashboardSessionLite`** (`color`/`sessionId`, no `recurrenceGroupId`) — reusing it needs a lossy adapter + a cross-feature import (FW-7). Build fresh: a `DashboardWeekStrip` (7 day columns, **today highlighted**, the **next upcoming session inverted (dark) + amber left-border + "· NEXT"** per s06) and a compact `DashboardSessionRow`. **`useSessions` is NOT used** — dashboard sessions are pre-bundled in the payload; a second `/api/sessions` fetch would double-fetch and re-bucket (the week is already tz-bucketed server-side, D16). "Open Schedule" footer routes to the existing schedule feature (read-only glance).
- **D6 — Reuse `PerfPill`/`perfTone`, `BandScoreChart`, `SkillPerfBars` where they fit; at-risk rails render `reasons[]` slugs.** At-risk rail rows (teacher + owner) show `name` + `attendanceRate` ("—" when null, never "0%") + `overallBand` ("—" when null) + `reasons[]` mapped to i18n (`dashboard.atRisk.reason.{attendanceBelowFloor|consecutiveMissed|bandDrop}`, en+vi) + `PerfPill tone="at-risk"`. **`perfToneFromStatus` is NOT a fit** — the dashboard sends `reasons[]` slugs, not an `AtRiskStatus`; pass `tone="at-risk"` directly. Student `recentFeedback` shows `overallBand` per submission as a lean mono value (the full `BandScoreChart` big-band block is heavier than a rail needs — reserve it for the analytics detail views in 8.3). **Student-facing decline is never red** (UX-DR22 → `--cl-muted`); AI confidence is hidden from students.
- **D7 — Owner storage capacity: adapt `LoadMeter` (or `ui/progress`).** `DashboardCapacity { storageUsedBytes, storageLimitBytes, percentUsed, approaching }`. **`percentUsed` is a 0..1 FRACTION** (0.80 = 80%) — display `Math.round(percentUsed*100)%`, do NOT render the raw fraction. `approaching===true` → amber treatment (`--cl-accent-2` decorative, `--cl-accent-2-text` for any text). Server sends `percentUsed: 0` when `storageLimitBytes` is 0 (div0 guarded server-side). Format bytes human-readable (check for an existing byte-format util; add one named `formatBytes.ts` if absent, CQ-3/CQ-4). `LoadMeter` (`components/domain/LoadMeter.tsx:31`, `{value, capacity, heavy}`) maps directly. **Plan-tier / seat capacity is NOT here** → FU-8-1-A (Epic 9), D-CAP.
- **D8 — Owner `needsAttention` renders the PRE-BUNDLED block; `NeedsAttentionList` is a visual template only.** Render `DashboardNeedsAttention` (`unassignedStudents{count,items}` / `atRiskStudents{count,items}` / `capacity` / `pendingInvites{count}`) in a fresh "Needs your attention" card echoing `NeedsAttentionList`'s color-coded amber-left-border zones — but do **NOT** mount `NeedsAttentionList` (`features/people/components/NeedsAttentionList.tsx:37`): it self-fetches the 7-3a `/api/enrollments/attention` endpoint → a redundant second fetch. Each row is an action link routing to the management surface (unassigned → roster; pending invites → staff; at-risk → roster/analytics).
- **D9 — One `OwnerDashboard` serves owner AND admin (both populate the `owner` block).** The discriminator (`role: 'owner'|'admin'`) distinguishes them only for **owner-only affordances** (UX §8.2 "Admin = Owner minus Owner-only affordances"). For v1 no material owner-only *dashboard* element is identified — render identically; gate any future owner-only element on `role==='owner'`. **Flag to Ducdo/Sally** if an admin-hidden dashboard element is wanted.
- **D10 — Owner/Admin get NO Q&A rail** (D-QA; epic-08 owner AC + Epic-7 R25/R26). The contract confirms it (`needsAttention` carries no Q&A block). Simply render none.
- **D11 — Rails: `block.count` is the true total; render ≤5 items + a "View all →" footer routing OUT.** Every `{count, items}` rail caps `items` at 5 server-side; show `count` as the headline and route the footer to the management surface (Needs grading → grading queue; Unanswered questions → Q&A; At-risk → roster/analytics; Due soon → assignments; My questions → Q&A). Dashboards are **read-only glances** (s06/s29 footer copy: "Read-only glance · click a session or Open Schedule to manage." / "Sessions are set by your teacher · read-only.") — **no mutations, no inline grading/reply**. At-risk `count` is capped by a 200-student scan server-side (documented summary approximation; the roster is authoritative — surface no "exact" claim).
- **D12 — Student s62 first-login = a durable client-side dismissal flag [RULED Ducdo 2026-09-15: "add a signal now"].** The payload has NO first-run flag and empty-array inference is forbidden (a returning student between terms would wrongly get the welcome); students never run the owner/teacher onboarding wizard, so there is no server signal. Gate s62 on a **durable per-user client flag** `localStorage['dashboard.student.welcomed:{userId}']` (mirrors the `useChecklistState` client-only-persistence precedent, FU-2-4). **Absent** → render the s62 guided welcome (forward-looking next-session hero + a short starter checklist + encouraging tone, per §6.4: ghost icon + Fraunces headline with one italic-accent word + muted one-liner + single primary action); **dismissed** (explicit CTA or first meaningful navigation) → set the flag, never show again. The flag is a **positive "has been welcomed"** signal (not empty-inference), so a returning student never false-triggers. Per-device caveat documented; a server-side cross-device signal = **FU-8-1-D**. The welcome is **additive** — it coexists with real data as it arrives, never blocks the cards.
- **D13 — Co-finalize the PROVISIONAL contract (8-1a D12).** Once the UI consumes every rendered field end-to-end, **strip the PROVISIONAL banner** from the `/api/dashboard` block in `api.yaml` + run `scripts/codegen.sh` (expect a comment-only/additive `client.ts` diff; any real shape change → atomic api.yaml+client.ts+backend commit, WF-4). web `tsc -b` = 0 (WF-6). The **4 shipped gaps** (at-risk `pendingCount` omitted; question-rail `className` omitted, only `classId`; due-item `className` omitted, no `classId` at all; owner over-capacity omitted) are **rendered-WITHOUT for v1** — rails show what ships (assignment title/skill, question content + `anchorExcerpt`). Whether to ADD any of them is a **code-review decision-needed** (mirror 7-2b's DN pattern) — each is a backend touch outside the default frontend scope; `dueItem` has no `classId` at all so a class label there needs a genuinely new field.
- **D14 — Mobile = responsive-now; purpose-built s82/s74 DEFERRED [RULED Ducdo 2026-09-15].** Ship all three dashboards **responsive** (Tailwind `md:`/`lg:` stacking, **44×44px** min touch targets, ≥16px inputs, horizontally-scrollable chip rows, **no body horizontal overflow** — wide content scrolls in its own `overflow-x-auto` container). The distinct **s82** teacher-triage tree ("is anyone blocked" first + the "Open in desktop for grading" desktop-only seam) and **s74** student single-due-now-hero tree + bottom tab bars are **OUT** → **FU-8-1-C**. The two mobile ACs are met at the **responsive-usability** level, not the purpose-built level (documented).
- **D15 — "Continue writing" deep-link (student `dueSoon`).** `dueSoon` item with `submissionId != null` → route to the writing editor for that submission (resume the draft); `submissionId === null` → route to start the assignment; `skill` from `dueItem.skill`. (The full s74 hero is deferred per D14, but the deep-link target logic ships in the responsive Due-soon card.)
- **D16 — `meta.serverTime` is the clock for ALL relative time (skew/hydration-safe).** Thread `serverTime` to the cards (prop, or a small `DashboardClockContext`). "Live now" (owner `todaySessions`) = `startsAt <= serverTime < endsAt` → amber. Due countdown = `deadlineAt − serverTime`. Question "N ago" = `serverTime − createdAt`. Grading `overdue` is **server-computed** — render the flag, do NOT recompute. Never `Date.now()`/`new Date()` in these paths (TS-6 spirit). Absolute day/week/"today" buckets are already server-computed in `centers.timezone` and CANNOT be re-bucketed client-side.

## Acceptance Criteria

### A. Route dispatch + role branch (retire /student)

1. **Given** any authenticated role navigates to `/dashboard`, **When** `useRole()` resolves, **Then** the `DashboardRoute` dispatcher mounts exactly ONE of `<OwnerDashboard>` (role `owner`|`admin`) / `<TeacherDashboard>` (`teacher`) / `<StudentDashboard>` (`student`) — three separate components (UX-3), each deep-imported for its own Rolldown chunk. **And** while `useRoleLoading()` is true, a checking/skeleton state renders (never the wrong dashboard).
2. **Given** the `/student` route stub (`routes.tsx:193-203`), **Then** it is **removed** and the student sidebar "Dashboard" entry continues to resolve `/dashboard` → `<StudentDashboard>` (no dead route remains; a route-inventory/precedence test asserts `/student` no longer matches).
3. **Given** `/dashboard` has no `RouteRoleGate`, **Then** all four roles reach the dispatcher (access is never denied by role — the branch is content), and the single `useDashboard` fetch (D3) is the only network call the page makes.

### B. Teacher dashboard (s06 — week-strip + 3 rails, onboarding-split)

4. **Given** a teacher whose onboarding is **incomplete**, **Then** the existing Epic-2 shell (`WelcomeBackBanner` + `FinishSetupCard` checklist) renders UNCHANGED (D2 preserve); the real dashboard does not replace it.
5. **Given** a teacher whose onboarding is **complete**, **When** `useDashboard` resolves, **Then** the real teacher dashboard renders: a `DashboardWeekStrip` over `teacher.weekSessions` (today highlighted, next session inverted + amber "· NEXT", D5) and three rails in order — **Needs grading** (`needsGrading.count` + ≤5 `items`: studentName · assignmentTitle · className · `overdue` flag), **Unanswered questions** (`unansweredQuestions.count` + ≤5 items: content + `anchorExcerpt` + "N ago" via serverTime), **At-risk students** (`atRiskStudents.count` + ≤5 items: name + attendanceRate("—"|%) + overallBand("—") + `reasons[]` i18n + `PerfPill`).
6. **Given** each rail, **Then** the headline count is `block.count` (true total) and a "View all →" footer routes to the management surface (D11); overdue grading items carry the overdue flag (server-computed, D16); the footer glance disclaimer renders ("Read-only glance · click a session or Open Schedule to manage").
7. **Given** loading / empty / error (UX-1 trilogy, mandatory), **Then** loading → skeletons mirroring the strip + rails (never a centered spinner); each empty rail → an informational empty state (role-appropriate, no management CTA — glance only); fetch error → an inline `role="alert"` with a retry calling `refetch` (not a full-page error).

### C. Owner/Admin dashboard (s48 — center pulse + needs-attention + storage capacity)

8. **Given** an owner **or** admin (one `OwnerDashboard`, D9), **When** `useDashboard` resolves, **Then** a **4-up center-pulse** stat row renders from `owner.pulse` (activeClasses · studentsEnrolled · staffActiveToday · sessionsThisWeek/sessionsToday) in Geist Mono numerals, distinct from personal teaching data.
9. **Given** `owner.todaySessions`, **Then** a "Today across the center" list renders each session with `teacherName` + `enrolledCount` (both non-null here) + class; a session with `startsAt <= serverTime < endsAt` is marked **"live now"** in amber (D16).
10. **Given** `owner.needsAttention` (D8, pre-bundled), **Then** a "Needs your attention" card renders color-coded amber-zone rows: unassignedStudents (count + ≤5 names) · at-risk (count + items) · **storage capacity** (`DashboardCapacity`: `Math.round(percentUsed*100)%` + human bytes, amber when `approaching`, D7) · pendingInvites (count) — each an action link routing out; **NO Q&A rail** (D10); **NO** plan/seat capacity (D-CAP); `NeedsAttentionList` is NOT mounted (no second fetch).
11. **Given** the trilogy, **Then** owner loading → pulse + card skeletons; empty needs-attention zones → per-zone empty copy; error → inline retry.

### D. Student dashboard (s29 — upcoming / due-soon / recent-feedback / my-questions)

12. **Given** a student, **When** `useDashboard` resolves, **Then** a greeting + dated summary, a read-only week-strip glance over `student.upcomingSessions`, and three rail cards render in order: **Due soon** (`dueSoon` ≤5, soonest deadline first: title + skill + countdown via serverTime + "Continue writing"/"Start" deep-link per D15), **Recent feedback** (`recentFeedback` ≤5: assignmentTitle + `overallBand` mono + releasedAt — **calmer treatment, decline never red**, UX-DR22), **My questions** (`myQuestions` ≤5 open threads: content + status + "N ago").
13. **Given** the student dashboard, **Then** it is **read-only** — no management actions, no class averages, no classmate/peer data anywhere (§8.4); the footer disclaimer renders ("Sessions are set by your teacher · read-only.").
14. **Given** the trilogy, **Then** loading → skeletons; each empty card → an encouraging student-tone empty state (§6.4 role tone); error → inline retry.

### E. Student first-login welcome (s62)

15. **Given** a student with `localStorage['dashboard.student.welcomed:{userId}']` **absent** (D12), **When** the student dashboard mounts, **Then** the s62 guided welcome renders (forward-looking next-session hero + short starter checklist + encouraging tone: ghost icon + Fraunces headline with one italic-accent word + muted one-liner + single primary action), coexisting with any real data.
16. **Given** the student dismisses the welcome (explicit CTA or first meaningful navigation), **Then** the flag is set and the welcome never renders again for that user on that device; a returning student (flag already set) never sees it. **Negative test:** an all-empty payload with the flag SET renders NO welcome (empty-inference is not used).

### F. Responsive, i18n, contract co-finalization, tests

17. **Given** D14, **Then** all three dashboards are usable at 390px: cards stack (`md:`/`lg:`), touch targets ≥44px, chip/filter rows scroll horizontally, and the page body never scrolls horizontally (wide content in its own `overflow-x-auto`). The purpose-built s82/s74 trees are **absent** (→ FU-8-1-C) — asserted by scope (no bottom-tab-bar mount in these chunks).
18. **Given** UX-2, **Then** every new string exists in BOTH `en.json` and `vi.json` under `dashboard.*` (net-new blocks: `dashboard.teacher.*`, `dashboard.owner.*`, `dashboard.student.*`, `dashboard.weekStrip.*`, `dashboard.atRisk.reason.*`, `dashboard.capacity.*`, `dashboard.welcome.*`); the i18n-parity test (`i18n-parity-coverage.test.ts`) passes; no hardcoded English; IELTS skill/band labels wrapped `<span lang="en">`; dates/counts via the i18n formatter (TS-6) / Geist Mono.
19. **Given** D13, **Then** after the UI validates every rendered field, the PROVISIONAL banner is stripped from the `api.yaml` `/api/dashboard` block; `scripts/codegen.sh` re-run; `client.ts` diff is comment-only/additive (any real shape change → atomic commit, WF-4); web `tsc -b` = 0. The 4 gaps (D13) are rendered-without (no `pendingCount`/class-name fabrication).
20. **Given** the test rules, **Then**: each role dashboard has the three-state trilogy (TEST-FE-1/2, MSW at the HTTP boundary — never mock `useQuery`); **role-branch proven — a student session's MSW payload is `{role:'student', student:{…}, teacher:null, owner:null}` and the DOM contains ONLY student cards (teacher rails + owner pulse ABSENT from the DOM, not merely hidden); a teacher payload renders teacher rails with owner/student absent; owner+admin both render `<OwnerDashboard>`** (TEST-FE-6, assert-absence); the s62 welcome shows on absent-flag / hides on set-flag / hides on all-empty-with-flag-set (D12 negative); `serverTime`-driven "live now"/countdown/"N ago" assert against the injected `meta.serverTime`, never a real clock; axe clean on each dashboard (TEST-FE-5); i18n key-existence en+vi (TEST-FE-4).
