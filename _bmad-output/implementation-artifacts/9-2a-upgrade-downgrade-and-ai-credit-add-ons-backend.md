## Story

As an owner,
I want to upgrade my plan (prorated, taking effect immediately), downgrade it (taking effect at my next renewal without ever losing data), and buy one-time AI-credit add-on packs — all processed through Polar.sh so ClassLite never touches raw payment data,
so that I can adjust my center's plan and AI budget as needs change, and so that Epic 9's billing UI (9-2b), payment-failure/grace handling (9.3), and every downstream money feature build on a real, signature-verified, idempotent Polar integration.

**Backend slice only — the Polar-integration keystone of the money half of Epic 9.** It lands: the `internal/polar` REST client (+ CI mock), the `internal/polarwebhook` HMAC verifier + the signature-verified `POST /api/webhooks/polar` receiver + the `polar_webhook_events` dedup table (D2 — pulled forward from 9.3), the add-on pack catalog + purchase → `addon_remaining` top-up (FR-64), the prorated-upgrade / at-renewal-downgrade write paths over the 9-1a `SetPlan` seam (FR-63), the `invoices` charge-snapshot table (D25), the extended owner-only `GET /api/billing` (next-invoice + payment-method + pending-downgrade — the D-DASH cards deferred from 9-1a), and the `BILLING_ENFORCEMENT_ENABLED` config plumbing + FU-9-CONTRACT-402 proof. No upgrade modal, no plan picker button, no add-on UI, no checkout VAT render, no invoice history page — those are 9-2b/9.3. The production arming flip stays OFF (deferred to post-9-2b, D3).

## Party-Mode Review Decisions (D17–D29 — v0.2, all FOLDED per Ducdo 2026-09-30)

- **D17 — Polar-driven plan change gets its OWN period-from-payload, change-gated seam — NEVER the genesis/override `SetPlan`. [BLOCKER — Winston+Murat+Amelia triple-convergence]** The shipped `SetPlan` (billing_service.go:503-547) unconditionally re-grants a FULL allocation (`grantPlanAllocationTx` zeroes `monthly_used`), stamps `current_period_end = clk.Now()+1month` (IGNORES `annual`), and writes `status='active'`. Polar fires `subscription.updated` for many non-plan reasons (payment-method change, metadata edit, renewal); routing each through `SetPlan` double-grants credits mid-cycle, forfeits `monthly_used`, and desyncs our period from Polar's (annual doubly wrong). Add a dedicated `SetPlanFromPolar(ctx, tc, tier, cycle, polarSubID, periodStart, periodEnd)` service method + its OWN query that: (a) writes `current_period_start/end` **from the Polar payload** (honors annual); (b) persists `polar_subscription_id`; (c) grants the monthly allocation ONLY on a genuine plan-change or period-rollover (compare incoming `period_start` to stored — an unrelated `subscription.updated` is a **no-op on credits/period**); for a mid-cycle upgrade, preserve `monthly_used` and top up to the new ceiling (do NOT re-zero). The override `SetPlan(Studio)` (D19/9-1a pilot seam) stays as-is (no Polar id, clock period). AC: mid-cycle upgrade preserves `monthly_used` + adopts Polar's `period_end`; unrelated `subscription.updated` = credit/period no-op. SUPERSEDES the AC13/AC16 "applies via the 9-1a `SetPlan` seam" wording.
- **D18 — Persist a `billing_checkout_intents` row at checkout-create + a read-triggered reconcile path for lost webhooks. [BLOCKER — Winston]** `POST /api/billing/checkout` returns the hosted URL and persists NOTHING today — a lost webhook (retries exhausted / endpoint-bug window) means money left the card and we have no record a checkout existed. Persist `billing_checkout_intents` (`center_id` RLS, `kind`, `target_plan`/`target_cycle`/`addon_pack_id`, `polar_checkout_id`, `status pending|applied|expired`, `created_at`) at create. On `GET /api/billing`, if an intent is `pending` beyond a threshold (≈60s), poll Polar (the AC1 get-subscription/get-order method — now wired) and apply/close it via the SAME idempotent apply path (D19/D22). This table is ALSO the tenant-resolution anchor (D20). AC: webhook never arrives → `GET /api/billing` reconciles the paid intent from Polar and applies it exactly once (shares event-apply idempotency).
- **D19 — ONE event type per side-effect + real unique keys + target-state idempotency (not event-id alone). [BLOCKER — Winston+Murat+Amelia]** One logical charge emits multiple distinct events (`checkout.updated`, `order.created`, `order.paid`, `subscription.updated`, `subscription.active`), each a different `webhook-id` — event-id dedup does NOT cover them. Dispatcher maps EXACTLY ONE event per effect: `order.paid` → invoice snapshot + add-on credit grant; `subscription.updated`/`.active` → plan/period apply (D17). All other events → 200 + log, NO mutation. Plan-apply is idempotent by **target-state check** (D17 period_start compare), not event identity. `invoices` gets `UNIQUE(polar_order_id)` + `ON CONFLICT DO NOTHING` (D22 ordering). SUPERSEDES the AC13 "or `order.paid`" ambiguity. AC: `order.paid` AND `subscription.updated` for one upgrade → exactly one invoice, one grant, one plan change (broader than AC14's same-event-twice).
- **D20 — Tenant resolution anchored on `billing_checkout_intents` (polar_checkout_id) FIRST, then persisted `polar_subscription_id`, then metadata — with a confused-deputy guard. [BLOCKER — Winston+Murat]** On the first-ever subscription there is no `polar_subscription_id` yet, and Polar's subscription/order event payloads may NOT carry the checkout `metadata` (provider-specific — VERIFY per-event-type field carriage against current Polar docs at dev time, cite in Dev Agent Record). ### patch

- [x] [Review][Patch] Poison-pill 500 → infinite Polar retry on a deterministic dispatch failure — a signature-valid, resolved-tenant event whose plan/cycle/interval doesn't map (`plan.IsValid` false, or `RecurringInterval` not literally `monthly`/`annual` — Polar likely sends `month`/`year`) returns a `ValidationError`; the handler maps ALL non-nil errors to 500 so Polar retries, and because the `polar_webhook_events` dedup INSERT shares the tx that rolls back, the retry re-inserts fresh and fails forever. The paid upgrade is never applied or recorded. Sibling arms (unparseable body, unresolved center, no owner, unknown pack, unknown event-type) all commit 200+log — this path should too (dead-letter), and/or map Polar's vocabulary before validating. [billing_polar.go:142-153, 268-274; webhook_handler.go:78-82]
- [x] [Review][Patch] Upgrade `order.paid` writes NO `invoices` row on the webhook happy-path — `applyOrderPaidTx` returns nil when `pack.Credits == 0` (every upgrade/renewal order.paid has no `addon_pack_id`), and the subscription-event path never inserts an invoice. Only the lost-webhook reconcile path writes a `kind='subscription'` invoice. Contradicts AC18/D10/D25 ("every charge flows through order.paid → invoices"). Normal webhook-delivered subscription charges have no snapshot → 9.3 invoice history will be empty. [billing_polar.go:188-193]
- [x] [Review][Patch] Reconcile apply-error permanently 500s `GET /api/billing` — `ReconcilePendingCheckouts` `continue`s on a Polar resolve failure but `return err`s on an `applyReconciledCheckoutTx` failure, and `GetUsageAndLimits` propagates it (`return BillingSummary{}, err`). One bad pending intent bricks the owner's billing dashboard on EVERY load and never marks the intent applied. Isolate per-intent apply failures (log+continue) like the resolve branch. [billing_polar.go:641-645; billing_read.go:146-147]
- [x] [Review][Patch] `parsePolarTime` zero-time corrupts the period and double-grants — a blank/unparseable `current_period_start/end` yields `time.Time{}`; the `genuine` check (zero ≠ stored) then writes `current_period_start = 0001-01-01`, re-points storage, grants the allocation, and surfaces `nextInvoice.DueDate = 0001-01-01`. A later real event is "genuine" again → a SECOND grant/ledger row. Treat a zero/unparseable period as do-not-apply (reject or 200-log), never write a sentinel + grant. [billing_polar.go:250-251, 284-286, 826-835]
- [x] [Review][Patch] `effectiveMax` swallows ALL DB errors as "no baseline" — `if err != nil { return planMax }` catches more than `pgx.ErrNoRows` (the comment's claim). A transient read error / cancelled ctx / RLS fault silently collapses a grandfathered ceiling back to `planMax`, wrongly blocking a legit create and hiding the fault. Branch on `errors.Is(err, pgx.ErrNoRows)`; propagate anything else (signature → `(int, error)`). Latent until arming (D3) but a fail-closed-wrong bug. [billing_service.go:149-161]
- [x] [Review][Patch] `latestLedgerBalance` swallows all errors as 0 — any non-`ErrNoRows` error returns balance 0, so the `balance_after` chain is computed against a false 0 and the append-only ledger audit chain breaks (the bucket update stays correct). Distinguish `ErrNoRows` (true 0) from a real error and propagate the latter. [billing_polar.go:424-429]
- [x] [Review][Patch] `invoices.subtotal_vnd` / `vat_vnd` are structurally always NULL — `insertChargeInvoice` sets only amount+currency; `SubtotalVnd`/`VatVnd`/`PolarInvoiceID`/`Description` are left zero-value → NULL, and `polarEvent` parses no split. AC18 says the snapshot records subtotal/vat. For add-ons the split is derivable from the (authoritative) snapshotted amount via `plan.Subtotal`/`plan.VAT`. [billing_polar.go:386-407]
- [x] [Review][Patch] Cancel⟷renewal race — no `(center)` lock, silent lying no-op — `ScheduleDowngrade`/`CancelDowngrade`/`UpdateSubscriptionFromPolar` take no advisory lock, so a cancel racing a renewal-apply is unserialized; `CancelDowngrade` unconditionally `ClearPendingDowngrade`s and returns nil even after the renewal already applied (the "silent lying no-op" D28(d) prohibits). D28(d)'s specified two-connection red is also absent. [billing_polar.go:518-585]
- [x] [Review][Patch] Charge currency never validated — `insertChargeInvoice` defaults blank→"VND" and stores `ev.Data.Amount` verbatim as `amount_vnd` with no check that the charge is actually VND in major units. A Polar `usd`/minor-unit amount becomes a wrong VND figure on the invoice/next-invoice card. Reject or flag `currency != "VND"`. [billing_polar.go:391-393]
- [x] [Review][Patch] `ScheduleDowngrade` accepts a same-tier or HIGHER target — only `plan.IsValid` + cycle are checked; the current tier is never compared. `POST /api/billing/downgrade {plan:studio}` while on Pro records a "downgrade" and schedules it at renewal with `proration_behavior:none`. AC15 says "for a LOWER tier." Add a strict tier-rank check. [billing_polar.go:518-525]
- [x] [Review][Patch] Pending downgrade recorded even when the Polar schedule is skipped — the `s.polar.ScheduleDowngrade` call is guarded by `PolarSubscriptionID.Valid && != ""`, but `SetPendingDowngrade` always writes the pending state. A paid center with an unbound sub id records a pending downgrade that nothing will ever apply at renewal, while the UI shows "scheduled." Fail/warn when scheduling a paid-plan downgrade with no bound subscription id. [billing_polar.go:542-559]
