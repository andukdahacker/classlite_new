## Story

As an Admin or Owner,
I want a staff roster read model (list + detail with workload/last-active), a working invite that actually emails the invitee, and Owner-only staff actions (assign-to-class, reset password, archive, force-logout),
so that the s39/s40/s41 UI (Story 7-1b) can render and operate the center's team over a correct, tenant-isolated, authz-enforced backend.

Backend slice only. The **s39 staff list / s40 detail / s41 invite modal UI is 7-1b**. Per D10 the staff read shapes + Owner-action response shapes are **provisional** — co-finalized when 7-1b is designed — but the backend behavior + tests are fully built here.

## Decisions (D1–D10 — all SPEC; D1/D6/D7 + the split are Ducdo rulings 2026-08-27)

- **D1 — Split (Ducdo).** 7.1 → **7-1a (Backend, this)** + **7-1b (Frontend s39/s40/s41)**. 7-1a is the keystone: it builds the read model + aggregates + invite delivery + action endpoints so 7-1b is pure UI wiring. Re-keys sprint-status (`7-1` → `7-1a`+`7-1b`).
- **D2 — Reuse + widen the canonical invite endpoint; make its email REAL.** The epic AC literally names `POST /api/staff/invite`, but the shipped canonical endpoint is **`POST /api/centers/{id}/invites`** (Story 2.6, `AdminInviteStaff` `auth_admin.go:72`). Do **NOT** create a second invite endpoint. Widen the existing one: request gains `name?`, `classId?`, `welcomeNote?`. Critically, `AdminInviteStaff` today **discards the raw token and sends NO email** (`auth_admin.go:194-198` — an explicit Epic-7 placeholder). 7-1a stops discarding it: mint the raw token, build the accept URL, render + enqueue the invite email (the `RenderInviteEmail` template + `EmailRetryQueue.Enqueue` already exist and are used by class-spawn/import — reuse verbatim). Persist `name` into the existing nullable `invites.name` column.
- **D3 — Staff list = a split-object response `{ members, pendingInvites }`, NOT a null-soup merged array.** Two genuinely different shapes (an accepted `center_members`+`users` row vs an unaccepted `invites` row) get two typed arrays. FE renders `members` in the active/archived tabs and `pendingInvites` (dimmed `??` avatar, UX line 464) in the pending tab, computing tab counts client-side (mirrors `ClassesPage.countByStatus`). **Owners are excluded entirely** from the roster (UX: "Owner excluded (managed in Settings)") — this also satisfies the epic AC "the Owner themselves are not listed." Surfaced roles: `admin`, `teacher`.
- **D4 — Status is DERIVED, no enum column. Add nullable `center_members.archived_at`.** `active` = `center_members` row & `archived_at IS NULL`; `archived` = `archived_at IS NOT NULL`; `pending` = an `invites` row with `accepted_at IS NULL`. Archive is a soft-archive (nullable timestamp), mirroring the repo's soft-delete convention ([[feedback_soft_delete_user_authored_content]]) — no hard delete of a member. Un-archive UI is deferred to 7-1b/later; the column + set-path ship here.
- **D5 — Load = rolling next-7-days scheduled-session count; capacity/heavy from named constants.** `sessionsPerWeek` = COUNT of `sessions` where `class_id ∈ (classes WHERE teacher_id = staffUserID)` AND `status='scheduled'` AND `starts_at ∈ [now, now+7d)`, tenant-scoped. `weeklyCapacity` = `DefaultWeeklySessionCapacity` (10). `heavy` = `sessionsPerWeek >= HeavyLoadThresholdSessionsPerWeek` (8). A rolling-window snapshot (not an ISO-week bucket) — deterministic, testable, and side-steps center-timezone week-boundary math. No stored weekly schedule exists (`sessions` are materialized dated rows, 3.4) so this is the only faithful "sessions/week" signal. Names are constants (CQ-3), not inlined.
- **D6 — Last active = `MAX(refresh_tokens.created_at)` per user (Ducdo).** Most-recent login / silent-refresh ≈ last active; cheap over `idx` on `refresh_tokens(user_id)`. **Nullable** — a fully-logged-out (or force-logged-out) user has no refresh row → `lastActiveAt = null` → FE renders "—"/"never". Documented caveat: this under-reports for a user who logged out; a dedicated `last_active_at` column was rejected (hot-path write + backfill, out of proportion to this story).
- **D7 — `invites.class_id` (nullable FK → classes) + auto-assign-on-accept (Ducdo).** Invite-time optional class is persisted on the invite. On acceptance, **iff** `invites.class_id IS NOT NULL` **and** the accepted role is `teacher`, set `classes.teacher_id = newMemberUserID` inside the existing accept-invite tx, honoring the `classes_teacher_mutex` (clear `pending_teacher_email`). A non-teacher invite may **not** carry a `classId` (422 at invite time). If the target class already has a teacher, acceptance reassigns it (Owner intent). This threads a small tweak into `acceptInviteAddMembership` (`auth_invite.go:283`).
- **D8 — Owner-only staff actions re-validate role from DB (SEC-1); force-logout is REUSE.** `archive`, `assign-class`, `reset-password` are Owner-only: middleware `RequireRole("owner")` at the edge **plus** a service-layer re-fetch of the caller's `center_members.role == owner` (never trust the JWT claim — mirrors `AdminInviteStaff`/`ForceLogout`). **Force-logout ships nothing new**: the shipped `POST /api/admin/users/{userId}/force-logout` (`AuthService.ForceLogout`, `auth_force_logout.go:48`, Owner-only, tenant-membership-guarded, audited) already does exactly FR-80 — 7-1b wires the s40 button to it. Reset-password reuses the `password_resets` token machinery (`RequestPasswordReset` internals) via a **new Owner-scoped entry point** keyed by target userId; the public self-service `POST /api/auth/forgot-password` (email-keyed, anti-enumeration) is untouched.
- **D9 — Recent activity + schedule glance from existing spines.** Detail `recentActivity` = last N `audit_logs` rows for `(center_id, user_id)` — a net-new `ListAuditLogsByUser` query over the append-only, already-indexed `audit_logs` (`idx (center_id, entity_type, created_at DESC)`; a user-scoped variant is added). `scheduleGlance` = next N `status='scheduled'` sessions for the teacher via the existing `ListSessionsByRange` join (`sessions.sql:45-60`, already exposes `c.teacher_id` + optional teacher filter). No new sessions/audit tables.
- **D10 — Read + action wire contracts PROVISIONAL (mirror 6-4a D16).** 7-1a is the producer; **7-1b is the sole consumer**. Build the read shapes (`StaffMember`, `PendingInvite`, `StaffMemberDetail`) + action responses as working contract with full tests, but mark them **provisional** in `api.yaml` — co-finalize during 7-1b design so the one UI consumer validates them before they harden. Expect refinement.

### Party-mode amendments (D11–D17 — SPEC; added v0.2 2026-08-27, Winston/Murat/John/Amelia + Ducdo rulings)

- **D11 — Single-owner / single-center-per-user invariant (Ducdo).** A center has exactly one Owner; a user belongs to exactly one center (the latter DB-enforced by `add_center_members_user_unique`, 2026-07-02). This makes **D3 faithful** (excluding owners from the roster = excluding the one acting owner; the epic's "the Owner themselves are not listed" holds) and **D6 clean** (a user's `refresh_tokens` cannot carry another center's activity → no cross-tenant timing bleed). State the invariant in code comments at both sites. If multi-center membership is ever introduced, D6's proxy must be revisited (Winston flagged the latent bleed).
- **D12 — Re-invite supersedes an EXPIRED invite (Ducdo — resolves John's deadlock).** The 2.6 dedup gate 409s on ANY unaccepted invite (`accepted_at IS NULL`, no expiry in the predicate), and there is no resend/revoke endpoint → an expired invite makes an email permanently un-invitable without SQL. Fix: on invite, if the sole existing unaccepted invite for `(center, LOWER(email))` is **expired** (`expires_at <= now`), **refresh it in place** (new token_hash, expires_at, role, name, class_id) instead of 409; only a **non-expired** unaccepted invite still 409s `INVITE_EMAIL_TAKEN`. This preserves the partial-unique index `idx_invites_center_email_active` (still ≤1 unaccepted row per center+email). Resend/revoke as first-class features stay deferred (Epic-7 FU-2-6-F).
- **D13 — Auto-assign correctness on the accept path (Amelia+Winston+Murat — the sharpest edge).** Three parts, all mandatory: **(a) class_id must reach the accept path** — the SECURITY DEFINER `get_invite_by_token_hash` fn + `loadInviteByTokenHash` (`auth_google.go:729`) do NOT return `class_id`; adding the column does not surface it. Add a **3rd migration** `CREATE OR REPLACE`ing the fn to return `class_id` + widen the Go scan (preferred over an in-tx re-fetch). **(b) Thread auto-assign into BOTH accept functions** — `acceptInviteAddMembership` (`:283`, existing-user + OAuth) AND `acceptInviteCreateUserAndMember` (`:332`, new-user — the HEADLINE flow); Task 6 named only the first. **(c) Re-validate the class IN-TENANT at accept time** — the `invites.class_id` FK bypasses RLS, so a stale/cross-moved classId must be re-checked under the accept-tx tenant GUC (`GetClass`); a class no longer in the tenant → controlled no-op/clean skip, NEVER a cross-tenant `UpdateClass`. This is an F-group adversarial red. Auto-assign fires on **all three** accept paths (state it; test the OAuth path, not just `POST /api/auth/accept-invite`).
- **D14 — Owner-reset is a NET-NEW entry point, not a call into `RequestPasswordReset` (Amelia).** `RequestPasswordReset` (`auth_reset.go:34`) is email-keyed and **silent-returns on unverified/unknown user** (`:47-69`) with a `padToFloor` anti-enumeration pad — a pre-provisioned/unverified staff member → silent no-op → violates AC15. The Owner-scoped path reuses only the **primitives** (`newPasswordResetToken`, `HashResetToken`, `CreatePasswordReset` + a `GetUserByID` for the target email, `RenderPasswordResetEmail`, `retry.Enqueue`), keyed by target userId, membership-guarded, **no verified-gate, no silent path, no padToFloor** (authenticated Owner, no enumeration surface).
- **D15 — Staff-action audits write `audit_logs`, NOT `auth_audit_logs` (Amelia).** Two tables exist; D9 `recentActivity` reads `audit_logs` via new `ListAuditLogsByUser`. The auth spine's `logAuthAuditBestEffort` writes `auth_audit_logs` — if staff actions follow it they never surface in `recentActivity`. Staff-action audits (`staff.class_assigned`/`staff.archived`/`staff.password_reset_requested`) MUST go through `InsertAuditLog` (`audit_logs.sql`), entityType `center_member`, so they feed the detail view. NB: `audit_logs` has no `(center_id, user_id)` index — `ListAuditLogsByUser` leans on `LIMIT N` (tolerable; add the index only if `EXPLAIN` says so). The column is `action` not `event` — the AC4 handler aliases it.
- **D16 — Load: bound `now` param + honest "next-7-days" naming + scheduleGlance status filter (Amelia+Murat+Winston).** `sessionsPerWeek`'s window `[now, now+7d)` takes `now` as a **bound `sqlc.arg`** (`s.clk.Now()` injected), never SQL `now()` — the codebase injects the clock and AC7 boundary reds need a fake clock (SQL `now()` = non-deterministic, deleted-later flake). Reuse `ListSessionsByRange`'s half-open `[from,to)` convention verbatim. **Rename the concept to `nextSevenDaysSessionCount` / "next-7-days load"** in the provisional contract (it is a SLIDING window, not a calendar week — do not label it "weekly" and let 7-1b harden a lie). `scheduleGlance` post-filters `status='scheduled'` in Go (`ListSessionsByRange` returns cancelled too) with a chosen upper bound (e.g. `now+30d`, `ScheduleGlanceWindowDays`).
- **D17 — Documented caveats + CRLF guard + visible archive ghost (Winston+John+Amelia).** (a) `lastActiveAt` caveats written down: force-logout DELETEs refresh rows → snaps `lastActiveAt` to `null`/"never" for a just-active user (D6+D8 interaction); plain logout that only sets `revoked_at` keeps the row → non-null. (b) The invite email interpolates `centerName` → apply `stripCRLFAndControls` (SMTP-header-injection guard, per `class.go:483`); `centers.name` has no CRLF ban. (c) Archiving a teacher does NOT auto-unassign classes (kept OOS), but the ghost must be **visible not silent**: the archive response includes `assignedClassCount` so 7-1b can warn "this teacher still owns N classes" at archive time (John: make the ghost visible, don't make it illegal).

## Acceptance Criteria

### A. Staff list read — `GET /api/staff`

1. **Given** an Admin or Owner calling `GET /api/staff`, **When** it runs, **Then** it returns `{ data: { members: StaffMember[], pendingInvites: PendingInvite[] } }` where `members` = every `center_members` row of this center with role ∈ {`admin`,`teacher`} joined to `users` (userId, name, email, avatarUrl, role, `status` ∈ {active,archived} per D4, `classesAssigned` count, `load {sessionsPerWeek, weeklyCapacity, heavy}`, `lastActiveAt` nullable), and `pendingInvites` = every `invites` row with `accepted_at IS NULL` and role ∈ {admin,teacher} (inviteId, name nullable, email, role, invitedAt, expiresAt, pendingClassId nullable). **And** owners are excluded from both arrays (D3), including the calling Owner.
2. **Given** a Teacher or Student calling `GET /api/staff`, **Then** 403 `INSUFFICIENT_ROLE` (staff roster is Admin/Owner only) — the middleware `RequireRole("owner","admin")` fires before the handler.
3. **Given** an archived member (`archived_at IS NOT NULL`), **Then** it appears in `members` with `status='archived'` (the FE segregates it into the Archived tab). **And** a `pendingInvites` entry never appears in `members` and vice-versa.

### B. Staff detail read — `GET /api/staff/{userId}`

4. **Given** an Admin or Owner calling `GET /api/staff/{userId}` for a member (role admin/teacher) of this center, **Then** it returns `StaffMemberDetail`: profile (userId, name, email, avatarUrl, languagePref), role, status, `assignedClasses[] {classId, name}`, `scheduleGlance[] {sessionId, classId, className, startsAt, endsAt}` (next N scheduled, D9), `load {sessionsPerWeek, weeklyCapacity, heavy}`, `lastActiveAt` (nullable), `recentActivity[] {event, entityType, at}` (last N audit rows, D9).
5. **Given** `GET /api/staff/{userId}` where the userId is not a center member, or is a `student`, or is an `owner`, **Then** 404 `STAFF_NOT_FOUND` (never 403 — do not disclose existence/role across the boundary).
6. **Given** a Teacher/Student caller, **Then** 403 `INSUFFICIENT_ROLE`.

### C. Load + last-active aggregates (query correctness)

7. **Given** the load aggregate (D5), **Then** `sessionsPerWeek` counts exactly the `status='scheduled'` sessions of the target teacher's classes with `starts_at ∈ [now, now+7d)` — cancelled sessions excluded, sessions outside the window excluded, other teachers' classes excluded, cross-tenant sessions excluded. `weeklyCapacity=10`, `heavy = sessionsPerWeek >= 8` (named constants). An admin (never a class teacher) yields `sessionsPerWeek=0, heavy=false`.
8. **Given** the last-active aggregate (D6), **Then** `lastActiveAt = MAX(refresh_tokens.created_at)` for the user, or `null` when the user has no refresh row. Tenant-scoped read; never leaks another user's tokens.

### D. Invite widening + real email delivery + auto-assign-on-accept

9. **Given** `POST /api/centers/{id}/invites` with `{ email, role, name?, classId?, welcomeNote? }` from an Owner/Admin, **Then** an `invites` row is created (7-day expiry, `token_hash`, `name` persisted, `class_id` persisted when present) **and** a real invite email is enqueued via `EmailRetryQueue.Enqueue` using `RenderInviteEmail(centerName, inviterName, role, acceptURL)` (welcome note appended, D2) where `acceptURL` embeds the **raw** token for the existing `POST /api/auth/accept-invite` flow. The raw token is no longer discarded.
10. **Given** the invite request, **Then** all shipped 2.6 guards still hold: role ∈ {owner,admin,teacher} else 422; **FR-11** Admin-invites-Owner → 403 `ROLE_ASSIGNMENT_FORBIDDEN` (`model.OutranksOwner`); duplicate active invite → 409 `INVITE_EMAIL_TAKEN`; SEC-1 caller-role re-validated from DB. **And** `classId` is accepted **only** when role=`teacher` (422 `VALIDATION_ERROR` otherwise, D7); a `classId` not in this center → 422/404 `CLASS_NOT_FOUND`.
11. **Given** an invite carrying `class_id` is accepted by a `teacher`, **When** `POST /api/auth/accept-invite` completes, **Then** in the same accept tx `classes.teacher_id` is set to the new member (mutex-honored: `pending_teacher_email` cleared), reassigning if the class already had a teacher (D7). **And** an invite with no `class_id`, or accepted by a non-teacher, leaves class assignment untouched. **And** the existing accept-invite behavior (membership upsert, `MarkInviteAcceptedGuarded`, session mint, audit) is byte-unchanged otherwise.
12. **Given** the invited staff member, **Then** they surface in `GET /api/staff` under `pendingInvites` until acceptance, after which they surface under `members` with `status='active'` (D4). Email send is best-effort (enqueue failure never fails the invite write — mirror class-spawn).

### E. Owner-only staff actions

13. **Given** `POST /api/staff/{userId}/assign-class { classId }` from an **Owner** on a `teacher` member of this center, **Then** `classes.teacher_id = userId` for that class (mutex-honored), 200 with the updated assignment. **And** target not a teacher member → 404 `STAFF_NOT_FOUND`; class not in center → 404 `CLASS_NOT_FOUND`.
14. **Given** `POST /api/staff/{userId}/archive` from an **Owner** on an admin/teacher member, **Then** `center_members.archived_at = now()`, 200; the member moves to `status='archived'`. **And** archiving self → 409 `CANNOT_ARCHIVE_SELF`; target an owner / non-member → 404 `STAFF_NOT_FOUND` / 409 as appropriate. (Class auto-unassign on archive is OUT OF SCOPE — D4/Out of Scope.)
15. **Given** `POST /api/staff/{userId}/reset-password` from an **Owner** on an admin/teacher member, **Then** a `password_resets` row is created and a reset email is enqueued to the member's address via `RenderPasswordResetEmail` (reuse the `RequestPasswordReset` token machinery, D8), 204. Target non-member → 404 `STAFF_NOT_FOUND`.
16. **Given** any of the three Owner-only actions (assign-class / archive / reset-password) called by an **Admin/Teacher/Student**, **Then** 403 `INSUFFICIENT_ROLE` — enforced at BOTH the middleware edge (`RequireRole("owner")`) AND a service-layer DB role re-fetch (SEC-1, D8). **And** force-logout (FR-80) requires **no new endpoint**: `POST /api/admin/users/{userId}/force-logout` already ships this Owner-only, tenant-guarded, audited — a regression assert confirms it is intact and reachable for a staff target (7-1b wires the button).

### F. RLS / tenancy / authz (adversarial — TEST-BE-1)

17. **Given** cross-tenant access, **Then** tenant A can neither READ (`GET /api/staff`, `GET /api/staff/{id}`) nor WRITE (archive/assign-class/reset-password) tenant B's staff — every store method takes `TenantContext` (GO-1) and every mutating tx sets `SET LOCAL app.current_tenant_id` (PERF-1); an adversarial test asserts tenant A's list omits tenant B members and each B-targeted action 404s.
18. **Given** the merged read (`center_members` + `users` + `invites` + `refresh_tokens` + `sessions` + `classes`), **Then** RLS on the tenant-scoped tables (center_members, invites, sessions, classes) is FORCE-enforced; the global `users`/`refresh_tokens` reads are keyed by ids already tenant-filtered upstream (a member/token is only read for a userId proven to be a center member first). No aggregate subquery escapes the tenant GUC.

### G. Migrations

19. **Given** the migrations, **Then**: (a) `center_members` gains `archived_at timestamptz` NULL (D4); (b) `invites` gains `class_id uuid` NULL FK → `classes(id)` (D7); each with a reversible `.down.sql`. RLS policies on both tables are unchanged (no new policy needed — the added columns ride the existing `center_id` grid). No data backfill.

### H. Security & tests (WF-8 HARD GATE — red-first before in-progress)

    - **★ Token round-trip (D2):** mint invite → pull `acceptURL` from the `MockEmailSender` payload → hash → == persisted `invites.token_hash` → feed raw token to `POST /api/auth/accept-invite` → membership created (proves the link WORKS, not just "enqueued"). **welcomeNote HTML/link payload escaped** in the rendered body (D17b anti-injection).
