## Story

As an owner,
I want the three plan tiers defined with their limits enforced server-side — teacher seats, classes, students-per-class, AI credits, and storage — so that a hard block prevents any action that would exceed my plan while my existing data and access are never degraded,
so that the plan model is a real, testable contract that the billing UI (9-1b), upgrades (9.2), and payment-failure handling (9.3) can all build on.

**Backend slice only.** This is the **keystone of Epic 9**: it lands the `subscriptions` + `ai_credits` schema, the `billing_service` that owns the locked plan model and every write-time limit check, the `INSUFFICIENT_CREDITS` gate that closes the P1 uncapped-Gemini-spend hole (FU-11-CREDITCAP), and the Owner-only read API the whole epic's UI reads from. No pricing page, no plan picker, no usage meters, no banners — those are 9-1b. No Polar integration, no upgrade/downgrade, no invoices — those are 9.2/9.3.

A DoD reconciliation test asserts `ai_credits.available == ledger-derived balance` after a grant/deduct/refund/addon sequence. `available = (monthly_allocation - monthly_used) + addon_remaining`.

A scheduled reset worker is a deliberate NON-goal (lazy-on-access is correct for the gate; a proactive worker for meter freshness can be a later FU).

- **D10 — R22 concurrency is the load-bearing invariant.** Every `Check*` is a read-then-write against a count that another concurrent request could also be incrementing. ## Party-Mode Review Decisions (D13–D26 — v0.2, all FOLDED per Ducdo 2026-09-28)

- **D13 — Credit advisory lock is CENTER-ONLY; all four check-types use the two-arg NAMESPACED form. [BLOCKER fix — Winston+Murat]** The v0.1 `pg_advisory_xact_lock((center,user))` for credits is a **lost-update bug**: `ai_credits` is center-scoped (one row/center), so two teachers in one center take different locks and clobber the same row — the exact R22 race. Use `pg_advisory_xact_lock(hash32(center_id), resource_class)` with `resource_class ∈ {seat=1, class=2, enrollment=3, credit=4}` (int4 pair). Credit consume/refund/reset ALL take `(center, credit)` — identical key across the three, so a reset can't interleave a consume (Murat). Document the UUID→int4 hash + accepted birthday-collision (worst case two centers occasionally serialize; correctness preserved). SUPERSEDES D5's `(center,user)` key and D10's per-resource wording.
- **D14 — `ai_credits` is a TYPED PROJECTION of the ledger head; reconcile on the SNAPSHOT, not sum-of-deltas. [BLOCKER fix — Winston+Murat, both proved the v0.1 DoD invariant mathematically false across a reset]** `sum(deltas) == available` breaks at every monthly reset (reset zeroes `monthly_used` + forfeits unused monthly credits; ledger only appends). Reframe D5: `ai_credits` is the ledger head decomposed into buckets, NOT a co-equal accumulator. **Invariants (both testable):** (1) `ai_credits.available == latest_ledger_row.balance_after`; (2) chain integrity `balance_after[n] == balance_after[n-1] + delta[n]`. The `monthly_grant` reset row sets `balance_after = new_allocation + addon_remaining` and `delta = balance_after − prev_balance_after` (equals `−monthly_remaining_prev + new_allocation`; the forfeit is thus auditable, no phantom +allocation). SUPERSEDES the AC14 "ledger-derived balance" wording.

## Acceptance Criteria

### A. Schema & genesis (subscriptions, ai_credits, backfill)

1. **Given** the migrations run, **Then** a `subscriptions` table exists — `id uuid PK`, `center_id uuid NOT NULL` **UNIQUE** FK→centers ON DELETE CASCADE, `plan text NOT NULL CHECK (plan IN ('free','pro','studio'))`, `billing_cycle text NOT NULL CHECK (billing_cycle IN ('monthly','annual'))`, `status text NOT NULL CHECK (status IN ('active','past_due','cancelled'))`, `polar_subscription_id text` (nullable), `current_period_start timestamptz NOT NULL`, `current_period_end timestamptz` (nullable — Free has none), `created_at timestamptz NOT NULL DEFAULT now()`, `updated_at timestamptz NOT NULL DEFAULT now()` — with RLS `ENABLE`+`FORCE`, `center_id = current_setting('app.current_tenant_id')::uuid` SELECT/INSERT/UPDATE policies (mirror `ai_credit_ledger` policy shape). **And** the `PLAN_LIMIT_EXCEEDED`/`INSUFFICIENT_CREDITS` behaviour never depends on JWT plan claims — plan is always read from this table.
2. **Given** the migrations run, **Then** an `ai_credits` table exists — `id uuid PK`, `center_id uuid NOT NULL` **UNIQUE** FK→centers ON DELETE CASCADE, `monthly_allocation integer NOT NULL`, `monthly_used integer NOT NULL DEFAULT 0`, `addon_remaining integer NOT NULL DEFAULT 0`, `reset_at timestamptz NOT NULL`, `created_at`/`updated_at` — with CHECKs `monthly_used >= 0`, `addon_remaining >= 0` — and RLS `ENABLE`+`FORCE` with the same tenant policies.
3. **Given** the genesis backfill migration, **Then** EVERY existing center gets exactly one `subscriptions` row (`plan='free'`, `status='active'`, `billing_cycle='monthly'`, `polar_subscription_id=NULL`, `current_period_start=now()`, `current_period_end=NULL`) and one `ai_credits` row (`monthly_allocation=0`, `monthly_used=0`, `addon_remaining=0`, `reset_at`=start of next month). **And** the backfill is idempotent (re-run inserts nothing — the UNIQUE(center_id) makes `ON CONFLICT DO NOTHING` a no-op). **And** the `.down.sql` drops both tables (reverse order, FKs first).
4. **Given** a NEW center is created (signup / center-create service), **Then** its `subscriptions` (Free) + `ai_credits` (0/0/0) rows are created in the **same tx** as the center — a center can never exist without them (else the gate divides by a missing row). A store/service test asserts both rows appear after center creation.

### B. Plan model (Go constants — D2/FU-4-4-4)

5. **Given** the `internal/plan` package, **Then** it holds the LOCKED three-tier map (single source of truth) with these exact values (epic:22-30 + blocker-resolutions A8) — Free / Pro / Studio: teachers `1 / 10 / Unlimited`; classes `1 / Unlimited / Unlimited`; studentsPerClass `5 / 20 / 60`; aiCreditsPerMonth `0 / 500 / 2000`; storageBytes `524288000 / 5368709120 / 53687091200` (500 MiB / 5 GiB / 50 GiB); priceMonthlyVnd `0 / 399000 / 999000`; priceAnnualVnd `0 / 3990000 / 9990000`. `Unlimited` is a named sentinel (`-1`). VAT is 10% inclusive: `subtotal = round(price / 1.1)`, `vat = price - subtotal` (Pro monthly → 362727 + 36273 = 399000). No `plan_limits` DB table exists (grep proves it).
6. **Given** a subscription's plan, **When** it is created or changed, **Then** `centers.storage_limit_bytes` is written from `plan.storageBytes` in the same tx (Free keeps the 500 MiB default; Pro→5 GiB; Studio→50 GiB). The existing `file_service` `StorageFullError` (409 `STORAGE_FULL`) enforcement is unchanged — it now reads a plan-driven ceiling. (9-1a only ever sets Free on genesis; 9.2 drives real plan changes.)

### C. Write-time enforcement (billing_service — D3/D10)

7. **Given** a center at its teacher-seat cap (e.g. Free = 1 teacher), **When** an owner/admin invites or adds another teacher (`staff_service`), **Then** `billing_service.CheckTeacherSeat` (inside the caller's tx, under a per-center advisory lock) returns `PlanLimitExceededError{Limit:"teachers", Current, Max}` → **409 `PLAN_LIMIT_EXCEEDED`** and the invite/add is NOT written. **And** Studio (Unlimited) never blocks. Teacher count = active `center_members` with role in {teacher,admin,owner-as-teacher — document the exact roles counted} (cite the count query).
8. **Given** a center at its class cap (Free = 1 class), **When** an owner/admin/teacher creates a class (`class_service`), **Then** `CheckClassLimit` blocks with `PLAN_LIMIT_EXCEEDED` (limit `classes`) before the class row is written; Pro/Studio (Unlimited) never block.
9. **Given** a class at its students-per-class cap (Free 5 / Pro 20 / Studio 60), **When** a student is enrolled (`enrollment_service`), **Then** `CheckStudentPerClass(classID)` blocks the (cap+1)th enrolment with `PLAN_LIMIT_EXCEEDED` (limit `studentsPerClass`, current/max the per-class count) before the enrolment row is written. Existing enrolments are untouched (D11). Count = active enrolments in that class (cite query).
10. **Given** two concurrent requests that would each take a center/class from `cap-1` to `cap` and then `cap+1` (R22 — the enrolment race is the canonical case), **When** both run, **Then** exactly ONE succeeds and the other gets `PLAN_LIMIT_EXCEEDED` — the per-center advisory lock serializes the read-then-write so both cannot read `cap-1` and both write. **WF-8 red test** (concurrent goroutines against a real DB tx per TEST-BE-2). Prove it FAILS without the lock (a synthetic no-lock variant lets both through).

### D. AI-credit gate (D-CREDIT / D5 / D6 — closes FU-11-CREDITCAP)

11. **Given** a center whose available credits `= (monthly_allocation - monthly_used) + addon_remaining` is `<= 0` (Free is always 0), **When** an AI job is enqueued (`ai_grade_service` grade / `ai_generation_service` generate), **Then** `billing_service.CheckAndConsumeCredit` — inside the enqueue tx, under the `(center,user)` advisory lock — returns `InsufficientCreditsError{Available}` → **402 `INSUFFICIENT_CREDITS`**, and NO job row and NO ledger deduction are written (rollback). This replaces the `ai_grade_service.go:62` *"There is NO 402 balance gate"* hole.
12. **Given** available credits `> 0`, **When** an AI job is enqueued, **Then** in one tx: (a) lazy-reset if `clk.Now() >= reset_at` (D6), (b) decrement — spend `monthly` (`monthly_used++`) until the monthly allowance is exhausted, THEN `addon_remaining--` (add-ons consumed AFTER allocation — FR-64), (c) insert the `-1 job_deduction` ledger row (existing `InsertJobDeduction`, idempotent on `(ref_job_id, reason)`). **And** the existing refund path (`RefundJob` on terminal failure) reverses BOTH: `ai_credits` (give back to monthly or addon) **and** the `+1 job_failed_refund` ledger row — kept consistent under the same lock.
13. **Given** two concurrent AI jobs when available `= 1` (R22 — the credit race), **When** both run, **Then** exactly ONE enqueues (credit spent) and the other 402s — never both. **WF-8 red test.**
14. **Given** the reconciliation invariants (D14 — SUPERSEDES the v0.1 sum-of-deltas wording), **Then** at all times `ai_credits.available == latest_ledger_row.balance_after` AND every ledger row satisfies `balance_after[n] == balance_after[n-1] + delta[n]`. The `monthly_grant` reset row sets `balance_after = new_allocation + addon_remaining`, `delta = balance_after − prev_balance_after`. A DoD integration test asserts BOTH invariants over a sequence that **includes a MockClock-driven monthly reset with an unused monthly remainder** (the case that breaks a sum-of-deltas check — the reset must not phantom-inflate the ledger).

### G. Party-mode hardening — arming, grandfather, credit-spend, contract, concurrency (D13–D26)

21. **Given** the enforcement flag `BILLING_ENFORCEMENT_ENABLED` (D19), **When** it is OFF (the 9-1a prod default), **Then** every `Check*` gate is a pure no-op — an over-cap create/enrol/invite/AI-job SUCCEEDS, and the schema + read API + credit accounting still run live. **When** it is ON, the gates 409/402 as specified. A test asserts both the OFF (succeeds) and ON (blocks) behaviour for at least one cap and the credit gate. **And** a plan-override seam exists (`scripts/seed.sh` path and/or an internal `SetPlan` store method) that sets a center to Studio (for pilot/dogfood).
22. **Given** grandfather semantics (D20), **When** enforcement is ON and a counted resource is at/over cap, **Then** a create is blocked iff `currentCount >= planMax` (computed via live `COUNT(...)` under the `(center,resource)` lock — never a stored counter), while ALL existing rows stay fully readable/editable (D11). Worked-example test: Free class seeded at 8 students (cap 5) → all 8 usable + editable; +1 → 409. 25. **Given** refund idempotency (D17), **When** `RefundJob` is called twice for one terminal-failed job, **Then** exactly one `job_failed_refund` ledger row exists and `ai_credits.available` is unchanged after the 2nd call (ledger-insert-first, `ai_credits` UPDATE gated on rows-affected). **And** a refund whose deduction month has already reset credits the `addon_remaining` bucket (never underflows `monthly_used`); a refund of a never-deducted job is a no-op.
26. **Given** the error contract (D23), **Then** `409 PLAN_LIMIT_EXCEEDED.details` = `{ limit: <stable enum TEACHER_SEATS|CLASSES|STUDENTS_PER_CLASS|STORAGE|AI_CREDITS>, current, max, canManageBilling: <bool> }` and `402 INSUFFICIENT_CREDITS.details` = `{ available, required }`. Covered races: seat/enrolment (AC10), credit at available=1 same center (AC13), and concurrent lazy-reset crossing `reset_at` → exactly one `monthly_grant` row + `reset_at` advanced exactly one month.
29. **Given** the money boundary (D25), **Then** the story/conventions record: `internal/plan` catalog is display-only; 9.2 invoices snapshot their own amount/vat; Polar is authoritative for charged amounts; VAT split is round-half-up integer VND; pricing/VAT-inclusive ratified by Ducdo 2026-09-28. (Documentation AC — no persisted reference to the Go price consts as historical truth.)
