## Story

As a **Teacher**,
I want **to trigger AI grading on a Writing submission and review its proposed band scores (with rationale + confidence) and anchored comments in the s23 grading view — accepting, editing, or dismissing each into my grading draft**,
so that **I grade essays in ~3 minutes instead of ~12 while remaining the one who commits the final grade.**

**Scope:** The frontend suggestion-review layer over the **shipped 6.1 s23 grading view** and the **shipped 6-2a backend** (endpoint + `AIWritingGradeResult` + `aiSuggestion` read). New: a `useAiGradeJob` enqueue+poll hook (clone of 4.3b `useAiGenerationJob`); an `AIGradeSuggestion` domain component (band-strip proposals + rail AI cards, per-item Accept/Edit/Dismiss, "Accept all praise", teacher-only confidence/rationale, disclaimer); merge-into-draft via a new `DraftComment.source` marker; a credit-cost confirm gate on every enqueue (FD4); the >30s/>60s slow messaging + non-blocking "ready — Review?" overlay + invalid-scores empty-form state + refund toasts; and the **live upgrade of the shipped static `FirstAIGradeCard`** to the UX-DR21 first-run flow.

**Explicitly NOT in this story:** any backend (6-2a shipped the endpoint, worker, result schema, refund, and `aiSuggestion` read); the grade write (6.1 `POST …/grade`, already consumed by `useGradeSubmission`); Speaking AI grading (6.3); the 402 balance gate + credit-history UI (6.5); config-driven auto-run (FU-6-2-A, deferred). See **Out of Scope**.

## Decisions (resolved during context recon — treat as spec, not suggestion)

- **FD1 — `useAiGradeJob` clones `useAiGenerationJob` verbatim, diffing only the endpoint + narrowing.** New hook in `src/features/grading/hooks/useAiGradeJob.ts` mirroring `src/features/exercises/hooks/useAiGenerationJob.ts`: enqueue = `useMutation` POST `/api/submissions/${submissionId}/ai-grade` with an **empty body** (`requestBody?: never` — the op takes none); poll = `useQuery<Job>` on the **reused `jobKeys.detail(jobId)`** (same `GET /api/jobs/{jobId}`); `BACKOFF_MS=[2000,4000,8000]`, `staleTime:0`, `retry:false`, hidden-tab ×3 multiplier, 5-min stuck timer, `POLL_FAILURE_LIMIT=3`. Result narrowing shim mirrors `asGenerationResult` → **`asWritingGradeResult` narrows `Job.result` on `'criteria' in result`** (the disjoint-oneOf discriminant — `AIGenerationResult` has `sections`, `AIWritingGradeResult` has `criteria`, 6-2a D11). **Handle the 200-idempotent response identically to 202** (both `EnvelopeJobEnqueued` → `{ jobId }`; a 200 means an in-flight job already exists → poll it, do NOT spend/expect a second credit — 6-2a D6).
- **FD2 — AI suggestions merge into the existing durable draft, never a parallel store.** Add `source: 'ai' | 'teacher'` to `DraftComment` in `src/features/grading/lib/gradingDraft.ts` — **client-only, never sent** (exactly like the existing `id`). Accepting an AI comment maps `AnchoredAISuggestion → DraftComment{ source:'ai', type, criterion, anchorStart, anchorEnd, text }` — **`confidence`/`rationale` are dropped at this map boundary** (`DraftComment` has no such fields), so they can never reach `grades` (6-2a D3, UX-DR22); accepting an AI band writes `draft.scores[criterion]=band` (the `band` number only — rationale/confidence not carried); the overall recomputes client-side via the existing `overallBandMath`. `buildGradeInput()` (WritingGradingPage) additionally omits the client-only `source` (as it already omits `id`) — the wire `AnchoredComment` / `criterionScores` shapes are UNCHANGED. Existing draft constructors (`commitComposer`, `draftFromGrade`) set `source:'teacher'`.
- **FD3 — Two "ready?" signals, kept separate (mirrors 6-2a D9).** The **triggering** teacher watches the creator-private poll via `useAiGradeJob`. A **reopen** (same teacher returns) or a **non-triggering** co-teacher/admin rehydrates suggestions from `view.aiSuggestion` — already flowing through `useGradingSubmission`, currently unused. NEVER drive a non-triggering teacher's "ready?" off the poll (`GET /api/jobs/{jobId}` is creator-private → 404 by design for a non-creator). On mount: if `view.aiSuggestion !== null` and no active job, render it as the reviewable suggestion set.
- **FD4 — Every enqueue is gated behind a credit-cost confirm; NO auto-enqueue on mount/remount (ratified 6-2a review, Ducdo 2026-08-20).** Per-run credit model: each run spends 1 credit. A single `AiGradeConfirmDialog` gates **both** the first run and any re-run — it shows the "−1 credit" cost (epic AC "credit cost shown before confirming") and the re-run warning when a completed `aiSuggestion` already exists. The grading view MUST NOT enqueue on render — only on the explicit CTA → confirm → enqueue path. (D6's in-flight index kills the *concurrent* double-fire; this dialog kills the *accidental re-charge on remount*.)
- **FD5 — Suggestions never auto-apply; the AI panel is additive.** On result arrival the proposals render in a review state; the teacher Accepts / Edits-before-applying / Dismisses each item; **"Accept all praise"** bulk-accepts praise-type comments only. Accepted items populate the draft; the teacher may still modify every field before Submit. Dismiss removes the proposal from the panel without touching the draft.
- **FD6 — UX discrepancy resolutions (the 3 flagged in the 6.2 hand-off):**
  1. **Card label vs in-view CTA are distinct surfaces, not a conflict.** The dashboard first-run card keeps **"Try AI grading"**; the in-view button is **"Run AI grading"** (sentence case, per spec §6.2 — overrides the epic AC's "Run AI Grading" capitalization).
  2. **Disclaimer = `"Suggestion — teacher always decides the final band."`** (em-dash, trailing period — the epic AC L100 acceptance contract, over the spec §6.2 middot draft). One i18n key.
  3. **Overall-band typography in the AI band-strip preview REUSES the exact treatment the 6.1 teacher overall band already renders** (Fraunces 32px per §9.1 s23 mockup; spec §2 rule "screen detail → mockup wins"). Do NOT introduce Geist Mono 28px in s23 — that catalog value (UX-DR22 / §5 token table) governs stat tiles elsewhere, not this screen. Match whatever `BandInputPanel`/`WritingGradingSurface` already ship so the AI preview and the teacher's own band read identically.
- **FD7 — The AI-suggestion card is a greenfield domain component `AIGradeSuggestion` in `src/components/domain/`** (cross-product s16/s17/s24). It composes/mirrors the shipped `CommentCard` chrome + a gradient **"AI"** avatar (vs the teacher's dark "You" avatar), renders the type/criterion tags + Accept/Edit/Dismiss + the **teacher-only** confidence badge (High/Medium) + rationale. Ships a `.stories.tsx` + `__tests__/` sibling (domain-tier convention). Confidence/rationale render on the teacher side ONLY — never reachable by the student `/result` path (which never receives `aiSuggestion`).
- **FD8 — First-run card is a SIMULATED run over the local fixture — no enqueue, no credit spent (RATIFIED, Ducdo 2026-08-20).** Upgrade the shipped static `FirstAIGradeCard` (`src/features/dashboard/FirstAIGradeCard.tsx`) to the UX-DR21 live *feel* without a real backend call: the CTA plays an animated ~15–30s progress ("AI đang phân tích bài viết…") then reveals the existing `sampleAIGrade.ts` fixture result with a subtle transition — **no celebratory modal**, **respect `prefers-reduced-motion`** (S-INFO-16). Rationale: the real endpoint requires a real teacher-of-class Writing `submissionId`; a demo must not seed a fake submission nor burn a live credit. Real AI grading is experienced in the s23 view on real submissions. **The card MUST NOT call `useAiGradeJob`/the enqueue endpoint** — the animation + reveal is purely client-side over the fixture.

## Acceptance Criteria

### A. Enqueue + poll + credit gate

1. **Run + confirm (epic AC "Run AI Grading"; FD4).** In the s23 view a **"Run AI grading"** control triggers an `AiGradeConfirmDialog` showing the **−1 credit** cost. On confirm, `useAiGradeJob.enqueue()` POSTs `/api/submissions/{submissionId}/ai-grade` (empty body) → the panel enters a *generating* state and polls `GET /api/jobs/{jobId}` with **2s → 4s → 8s** backoff. **No auto-enqueue on mount/remount** — the panel is idle until the teacher confirms.
2. **Idempotent 200 (FD1/6-2a D6).** A `200` enqueue response (an `ai_grade_writing` job is already pending/processing for this submission) is handled identically to `202` — the returned `{ jobId }` is polled; the UI does not imply a second credit was spent.
3. **Re-run gate (FD4; ratified per-run model).** When a completed `aiSuggestion` already exists, "Run AI grading" opens the same confirm dialog with an explicit re-run + re-charge warning; a fresh job enqueues only on confirm. Reopening/remounting the view with an existing suggestion NEVER re-enqueues.

### B. Suggestion review (band strip + comment rail)

4. **Band-strip proposals (epic AC L96-106; §9.1).** On `complete`, the AI band strip renders the four criterion proposals — each `{ band, rationale, confidence }` — with a per-criterion **Accept / Edit / Dismiss**, plus the analyzed-meta line **"analysed {analyzedWordCount} words · {latencyMs→s}"** (British "analysed", middot) and the disclaimer **"Suggestion — teacher always decides the final band."**. A preview of the AI overall band uses the FD6.3 treatment. Accept writes `draft.scores[criterion]`; Edit lets the teacher change the band before applying; Dismiss drops the proposal.
5. **Rail AI cards (epic AC; §9.1 L541).** AI anchored comments render as `AIGradeSuggestion` cards in the comment rail — visually separated from teacher cards (gradient "AI" avatar vs dark "You"), each with type tag (Error red / Praise green / Suggestion amber), criterion tag, **teacher-only confidence badge**, and **Accept / Edit / Dismiss**. Accept appends a `DraftComment{ source:'ai' }` anchored via the shared `essayAnchors` resolver; Edit opens the comment text/criterion for change before applying; Dismiss drops it.
6. **Orphan → general (epic AC L137-139; 6-2a already demotes).** A suggestion with `anchorStart/anchorEnd === null` (the worker demoted an unmappable anchor to whole-essay) renders as **general (unanchored) feedback**, never dropped.
7. **Accept all praise (epic AC L102-106).** A bulk **"Accept all praise"** action accepts every praise-type AI comment into the draft in one action; other types are untouched. Accepted suggestions populate the draft but the teacher can still modify before Submit — **nothing auto-applies on load (FD5).**
8. **Confidence + rationale are teacher-only (UX-DR22; 6-2a D3).** Confidence badges and rationale appear only in the teacher grading view. On accept they are DROPPED — `buildGradeInput()` sends neither (wire `AnchoredComment`/`criterionScores` unchanged). Negative test: the student `SubmissionReviewPage`/`GradedEssay` path renders NO confidence/rationale/AI-chip for an accepted comment (it reads as the teacher's own).

### C. Rehydrate + non-triggering reader

9. **Reopen rehydrate (FD3; 6-2a D2).** Reopening the grading view (no active job) with `view.aiSuggestion !== null` renders the latest suggestion set as reviewable — the teacher resumes Accept/Edit/Dismiss. Suggestions already merged into a persisted draft are not duplicated.
10. **Non-triggering teacher (FD3/6-2a D9).** A co-teacher/admin who did not trigger the run sees the suggestion via `view.aiSuggestion` (class-shared), NEVER via the creator-private poll. The UI must not attempt to poll a job it did not create.

### D. Slow + failure paths

11. **Slow messaging (epic AC L141-143).** While polling: after **30s** show "Taking longer than expected — AI is still working"; after **60s** show "This is unusually slow — you can start grading manually and AI suggestions will appear when ready". (Thresholds are elapsed-since-enqueue, distinct from the 5-min hard `stuck`.)
12. **Non-blocking ready overlay (epic AC L145-147; FD3).** If the teacher has started manual grading (draft dirty) while the job is still processing, result arrival shows a **non-blocking** "AI suggestions are ready — Review?" overlay with a merge-into-existing-work action — it does NOT auto-open the panel or clobber in-progress work.
13. **Invalid-scores empty-form state (epic AC L133-135).** On terminal `errorDetails==='invalid_band_scores'` show "AI produced invalid scores — please grade manually" with **all form fields empty** (never pre-filled with bad data). On `invalid_ai_response` (malformed/incomplete) show the "AI returned invalid output. Credit returned. Please grade manually." refund toast.
14. **Refund toasts (epic AC L149-155).** Terminal `failed` (max-retries / stuck) → toast "AI grading failed. Credit returned. Try again later or grade manually."; malformed/`invalid_*` → "AI returned invalid output. Credit returned. Please grade manually." (The refund itself is backend/6-2a; the FE only surfaces it.)
15. **Loading/Empty/Error trilogy (UX-1/UX-DR24).** The AI panel uses skeletons mirroring the final layout (no centered spinner), an inline retry on poll error (not a full-page error), and all copy via i18n (no hardcoded English, no HTTP codes).

### E. First-run card (UX-DR21 / FU-2-4-F)

16. **Live first-run upgrade (epic AC L124-129; FD8, ratified simulated).** The dashboard **"Try AI grading"** card's CTA plays an animated ~15–30s progress ("AI đang phân tích bài viết…") then reveals the `sampleAIGrade.ts` fixture result with a subtle transition — **no celebratory modal**, **respects `prefers-reduced-motion`**. This is a **simulated** run: purely client-side over the fixture, **no enqueue, no credit, no `useAiGradeJob`**.

### F. i18n + a11y

17. **i18n parity (UX-2 / TEST-FE-4).** Every new string is a `grading.ai.*` (and first-run) key added to BOTH `en.json` AND `vi.json` in the same change; the Vietnamese progress string is `"AI đang phân tích bài viết…"`. A `STORY_6_2B` closed-literal key list + prefix-ratchet parity test asserts both locales.
18. **Accessibility (TEST-FE-5 / UX-DR16).** The AI panel + confirm dialog pass axe; Accept/Edit/Dismiss are reachable by role/label; the ready overlay uses `aria-live` (async announcement); focus returns to the trigger on dialog close.

## Dev Notes
