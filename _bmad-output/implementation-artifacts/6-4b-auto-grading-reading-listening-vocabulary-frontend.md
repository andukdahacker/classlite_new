## Decisions (D1–D10 — SPEC; co-finalize 6-4a's D16. D9/D10 + the two [NEEDS DUCDO] flags added at pre-dev party-mode 2026-08-27: Winston/Sally/Murat/John)

- **D1 — Detect objective by `autoGrade` presence, NOT `exercise.skill` — with a distinct FAILED-grade fall-through (Winston).** `GradingRoute` dispatches to the objective page **iff `view.autoGrade != null`**, inserted **before** the skill check (`GradingRoute.tsx:51`). `exercise.skill` does NOT identify objective — 6-4a sets `autoGrade` only for an exercise with ≥1 gradable group (6-4a D3). **Edge (real, Winston #3):** an objective exercise (`skill ∈ {reading, listening, grammar, vocabulary}`) whose auto-grade FAILED at submit via 6-4a's D13 SAVEPOINT fault boundary writes **no working row** → `autoGrade` is `null` even though the exercise IS objective. Keying on `autoGrade` alone then falls through to the skill check and mislabels a *supported-but-failed* reading exercise as `grading.error.unsupportedSkill` — a misleading dead-end that masks a systemic grading failure. **Fix (AC16):** the fall-through branches on skill — `autoGrade == null && skill ∈ objectiveSkills` → a distinct `objectiveGrading.autoGradeUnavailable` state (honest "auto-grade unavailable" + retry affordance), NOT the unsupported-skill alert. `unsupportedSkill` remains only for genuinely non-objective, non-writing/speaking skills. (D1's "never use skill" is correct for the *positive* dispatch; the *error* branch legitimately needs skill to tell supported-but-failed from unsupported.)
- **D2 — `apiFetch`, not zodios; SPLIT the invalidation sets (Winston #1).** No zodios client; `src/lib/api/client.ts` is openapi-typescript **types only**, all calls through hand-written `apiFetch<T>` (`src/lib/api-fetch.ts:166`, `ApiError :67`, Bearer TS-8). The two new hooks copy `useGradeSpeaking.ts` — swap type + URL — **but do NOT copy its invalidation set verbatim.** An **override** does not change queue membership (submission stays un-released, still in the queue) → invalidate **`gradingKeys.detail(submissionId)` ONLY**; invalidating `gradingKeys.all` on every single-click override spuriously nukes the queue-list cache and forces a queue refetch per toggle. A **release** flips `submitted→graded` (membership changes) → invalidate **`detail` + `all`**. `retry:false` both (FW-6 — invalidation in the mutation, never a store).
- **D3 — Server is authoritative on scoring; the UI NEVER recomputes.** `percentage`/`provisionalBand`/`rawScore` live in the Go engine (6-4a D6/D7 — provisional EXCLUDES unresolved `needs_review` from the denominator: `resolvedCorrect / (maxScore − unresolvedNeedsReview)`). The "After-overrides" score is read **verbatim** from the override endpoint's returned `AutoGradeView`. The UI computes no band/percentage/denominator — it renders server numbers. The needs_review release-delta (D9) is likewise a *server-provided* projection or server-arithmetic — NOT a client recompute (see the [NEEDS DUCDO #1] flag).
- **D4 — Release is irreversible + notifies the student → confirm dialog with the reckoning (D9).** `POST /api/submissions/{id}/release` (NO body) → `EnvelopeGrade`. Reuse the `ReleaseConfirmDialog` shape (`SpeakingGradingPage.tsx:1126`) but NOT its copy verbatim — see D9. On success the composite-`key` remount re-seeds from the refetched view (`autoGrade.released:true`); breakdown flips read-only (D5/AC12). **Key trimmed to `${sid}:${autoGrade.released ?? false}` (Winston #4)** — `submission.status` (`submitted→graded`) is collinear with `released` (same event), so the 3-part key carried a redundant passenger. `canRelease` for objective is effectively always true (auto-grade produced numbers) — state it, don't inherit the speaking dialog's undefined gate. Handle the 409 trio as non-blocking toasts (UX-1, i18n).
- **D5 — Single-click override, NOT a form (FW-8 N/A) — with explicit row states (Sally).** Each row carries correct/wrong buttons → `overrideMutation.mutate({questionRef, mark})`. No RHF, no Zod form — the only input is the two-value `OverrideMark` enum (`correct|wrong`). `needs_review` is never an override **target** but IS a **source** (resolve a needs_review by overriding it correct/wrong). Three states the dev MUST build, not infer: **(a) toggle-back** — re-clicking the other mark flips a correct↔wrong override (fine); resolving a `needs_review` to a mark is a **one-way door** (the enum has no "clear back to needs_review" and the request has no un-override) — this is intended; the flag affordance is visibly *consumed* once resolved so the teacher sees it's done. **(b) in-flight** — override is a server round-trip returning the full recomputed view; disable that row's buttons (and ideally sibling rows) while the mutation is pending to prevent racing recomputes / a flashing band. **(c) post-release** — override controls disabled/absent when `autoGrade.released` (the immutability trigger 409s; don't offer the futile call).
- **D6 — Desktop-only; reuse the seam (UX-4).** Grading is desktop-only by design (`s87`/`s83`, UX §9.4). Reuse `useIsDesktop()` + `DesktopOnlySeam` (`SpeakingGradingPage.tsx:1232`, copy `grading.mobileSeam.*`). No bespoke mobile breakdown tree.

## Story

As a Teacher,
I want to open an auto-graded objective (Reading/Listening/Grammar-section, incl. Vocabulary-skill) submission in the grading view and see a per-answer breakdown I can correct with a single click before I release,
so that I review instant objective marks fast, override the edge cases, and the student only ever sees a grade I have released.

Frontend slice only. Consumes 6-4a's frozen backend contract (auto-grade-on-submit already ran; the working row already exists). The **student** per-question result view is **FU-5-5b-QUIZ** (deferred). This story co-finalizes the 6-4a override/release wire contract (D7).

## Acceptance Criteria

### A. Dispatch (GradingRoute third branch)

1. **Given** a teacher opening `/classes/{id}/grading/{aid}/{sid}` for an **objective** submission (`GET …/grading` returns `autoGrade != null`), **When** `GradingRoute` dispatches, **Then** the new objective grading page renders. The `autoGrade`-presence check runs **before** the `skill` check (`GradingRoute.tsx:51`), so a reading/listening/grammar submission no longer dead-ends at `grading.error.unsupportedSkill`. **And** writing/speaking submissions are unaffected (still dispatch to their existing pages — regression assert), **and** a genuinely ungradable skill (no `autoGrade`, not writing/speaking, not an objective skill) still shows the unsupported alert.
2. **Given** the route + page, **Then** the UX-1 trilogy is present by reuse: **loading** → the dispatch/preparing skeleton (`role="status"`); **error** → `role="alert"` + retry (reuse `GradingError`, `grading.error.*`); **not-desktop** → the `DesktopOnlySeam` (D6). No bare spinner, no blank container.

### B. Summary band (s25 §9.3)

3. **Given** the objective page, **Then** the summary band shows the big fraction `rawScore / maxScore`, the `provisionalBand`, and an **"After-overrides"** recomputed score that updates live after each override. **Every** displayed number is read from the `AutoGradeView` the server returned — the UI computes no percentage, band, or denominator (D3).
4. **Given** unresolved `needs_review` answers, **Then** the band surfaces their count and a plain-language note that **releasing counts unresolved needs_review as wrong** (D3/6-4a D10), AND a non-blocking resolve-nudge ("N flagged unresolved — [Jump to first]", `flattenQuestions` order, D9). The passive band note is NOT the primary defense — the reckoning lives at the release click (AC10/D9).

### C. Answer-review table (per-answer breakdown)

5. **Given** the breakdown, **Then** each answer row shows: the question number + `questionText`, the `studentAnswer`, the `correctAnswer` shown **when the effective mark is wrong or needs_review** (the key; a deliberate narrowing of the epic's flat "show correct answer" — the teacher doesn't need the key on a ✓ row, see Out of Scope), a Result chip (✓ correct / ✕ wrong / ⚑ needs-review) driven by `effectiveMark` (`overrideMark ?? autoMark`), the student's own `studentFlagged` "review later" indicator (informational), an **"edited" affordance when `overrideMark != null`** so the teacher can tell their own overrides from raw machine marks on re-open (D10), and per-answer **Override** correct/wrong buttons with an in-flight disabled state (D5).
6. **Given** a `needs_review` answer (free-text spelling variant, e.g. "hydro-electric" vs "hydroelectric"), **Then** the row is a first-class *resolution* affordance (this is the cognitive point of s25, not a generic row): visually distinct flagged state, the `studentAnswer` and `correctAnswer`/`acceptedVariants` shown side-by-side so the near-miss is judgeable, and the two override buttons framed as the resolution ("Accept as correct" / "Mark wrong") — resolving it consumes the flag (one-way, D5). **Negative:** `correctAnswer`/`acceptedVariants` render only in this teacher view — no student-facing surface is built (D8; leak-guard is backend-enforced).
7. **Given** the answer list, **Then** rows render in **document order grouped by section + group** via `flattenQuestions(view.exercise)` (`attemptContent.ts:90`) keyed by the colon `questionRef` handle (`{sec}:{grp}:{q}`) — never index-sorted arbitrarily. `TeacherGradingView.exercise` is typed `AttemptExercise`, the exact input `flattenQuestions` consumes (direct reuse, no adapter).

### D. Override (single-click, live recompute)

8. **Given** a teacher clicking correct/wrong on a row, **When** `overrideAutoGradeAnswer` succeeds, **Then** the breakdown row's `effectiveMark` + `overrideMark` and the summary band's After-overrides score reflect the recomputed `AutoGradeView` immediately — seeded from the `200 EnvelopeAutoGradeView.data` (`setQueryData(gradingKeys.detail, prev => ({...prev, autoGrade: data}))`, which renders **without waiting for the invalidation refetch** — that is the point of seeding) AND invalidated on settle (`detail` ONLY, not `all` — D2). During the round-trip the row's buttons are disabled (D5 in-flight). No client-side score math (D3).
9. **Given** an override failure — 409 `SUBMISSION_ALREADY_RELEASED` / `SUBMISSION_NOT_OBJECTIVE` / `AUTO_GRADE_NOT_FOUND`, 422 `INVALID_QUESTION_REF`, 404 `SUBMISSION_NOT_FOUND` — **Then** a non-blocking toast surfaces the i18n error, **each code resolving a DISTINCT message** (the three 409s share a status but must not collapse to one generic string — discriminate on `code`, not status), and the cached breakdown is NOT corrupted (no dangling write — because the seed is on-success only, a failed override leaves the prior view standing). Six codes, six named tests (AC15).

### E. Release (deferred, irreversible, notifies)

10. **Given** the teacher clicking **"Release result & notify"**, **Then** a confirm dialog (reuse `ReleaseConfirmDialog` shape) explains the student is emailed AND — **when unresolved `needs_review` > 0** — shows the reckoning: the flagged count and the provisional→released delta ("reviewing X/max · Band B₁; student receives Y/max · Band B₂", D9), with the released number the last thing before the confirm button. On confirm, `POST …/release` (no body) → on `200` a success toast + the composite-`key` remount (`${sid}:${released}`) re-seeds from the refetched view (`autoGrade.released:true`), so the student's `/result` now shows the released grade (reader contract, 6-4a AC18). `canRelease` is always true for objective (auto-grade produced numbers) — stated, not inherited from the speaking dialog's undefined gate (D4).
11. **Given** a release failure (409 trio), **Then** a non-blocking toast surfaces the i18n error; the page stays usable (no navigation, no data loss).
12. **Given** a **released** objective submission, **Then** the breakdown is read-only — override controls are disabled/absent (the D9 immutability trigger would 409; the UI must not offer the futile call), and the summary band shows the definitive released state. **Regression:** re-opening a released submission renders the read-only reviewed state, not a fresh editable one.

### The 6-4a contract this story consumes (FROZEN — co-finalized by D7)

Read from generated `src/lib/api/client.ts` via `import type { components } from '@/lib/api/client'` (openapi-typescript, types only — there is NO zodios client; all calls go through `apiFetch<T>`).

- **`GET /api/submissions/{id}/grading`** → `TeacherGradingView` (already fetched by `useGradingSubmission`). Additive **`autoGrade?: AutoGradeView | null`** (`client.ts:3357`) — present ONLY for objective submissions; null for writing/speaking. **This is the objectivity signal (D1).**
- **`AutoGradeView`** (`client.ts:3360`): `{ rawScore:number, maxScore:number, percentage:number, provisionalBand:number, released:boolean, answers:AutoGradeAnswerView[] }` **+ NEW `releasedProjection:{rawScore:number, band:number}` (this story, #1=A)** — the definitive as-if-released score/band (unresolved needs_review → wrong over full denom); the D9 dialog reads it verbatim.
- **`AutoGradeAnswerView`** (`client.ts:3368`): `{ questionRef:string (colon handle "{sec}:{grp}:{q}"), questionText:string, studentAnswer:string, studentFlagged:boolean, correctAnswer:string (teacher-only), acceptedVariants:string[] (teacher-only), autoMark:AutoMark, overrideMark:OverrideMark|null, effectiveMark:AutoMark }`.
- **`AutoMark`** = `correct|wrong|needs_review` (`needs_review` free-text near-miss only). **`OverrideMark`** = `correct|wrong` (never `needs_review`).
- **`POST /api/submissions/{id}/auto-grade/overrides`** — body `OverrideAutoGradeAnswerRequest {questionRef, mark:"correct"|"wrong"}` → `200 EnvelopeAutoGradeView` (`{data:AutoGradeView, meta}` — unwrap `.data`, the **full recomputed breakdown**). Errors: 409 `SUBMISSION_ALREADY_RELEASED`/`SUBMISSION_NOT_OBJECTIVE`/`AUTO_GRADE_NOT_FOUND`, 422 `INVALID_QUESTION_REF`, 404 `SUBMISSION_NOT_FOUND`.
- **`POST /api/submissions/{id}/release`** — **NO request body** → `200 EnvelopeGrade` (`.data`). Reuses the 6.1 atomic grade+release path (flips `submitted→graded`, enqueues the notification). Errors: 409 trio. **Distinct from** the writing/speaking `POST …/grade` endpoint.
- **Scoring semantics (D3, from 6-4a D6/D7/D10):** provisional `percentage = resolvedCorrect / (maxScore − unresolvedNeedsReview) * 100` (denom-0 guard → 0%); band from a Go percentage→band ladder. At **release**, unresolved `needs_review` counts as **wrong** over the full denominator → the released band can be lower than the pre-release provisional. Surface this (AC4). **The UI never recomputes — it renders server numbers.**
